# 资源 URL 落库与回显统一修复设计

## 背景

当前项目中，图片资源与视频资源的生成、上传、重绘、重生成链路存在一类系统性问题：

1. 资源服务层已经返回了最终可访问地址（尤其是 OSS URL）。
2. 调用方没有使用该最终返回值，而是继续按本地输出路径回写数据库。
3. 前端展示层有些 helper 只支持本地相对路径，不支持完整 `http(s)` URL。

其结果是：

- 资源实际上已经上传到 OSS；
- 但数据库中保存的仍是本地相对路径；
- 前端继续拼接 `/static/...` 访问本地文件；
- 本地文件可能已经删除或从未保留，最终出现 404 或回显错误。

已确认的封面链路即属于这一问题模式。用户要求将修复范围扩展到所有图片资源和视频资源生成链路。

## 本次目标

统一所有图片与视频资源的“最终地址落库规则”和“前端回显规则”，避免同类路径不一致问题重复出现。

### 统一规则

- 若资源最终拿到的是完整 `http://` 或 `https://` URL，则数据库直接保存该 URL。
- 若资源最终没有 OSS URL，只存在本地文件，则数据库保存现有本地相对路径。
- API 响应继续直接返回数据库保存值，不额外改写字段名或响应结构。
- 前端展示时：
  - 若字段值是完整 `http(s)` URL，则直接使用；
  - 若字段值是本地相对路径，则按既有 `/static/...` 规则转换。

## 范围

### 包含

- 图片资源
  - 小说封面
  - 漫画生成图片
  - 故事版图片
  - 角色参考图
  - 场景资产图
  - 道具资产图
  - 其他复用 `image2`/图片上传链路的资源

- 视频资源
  - 视频生成结果
  - 视频上传替换结果
  - 视频重生成结果
  - 其他复用视频上传/落盘/OSS 上传链路的资源

- 前端资源 URL helper 与展示入口

### 不包含

- 数据库 schema 变更
- 旧数据批量迁移
- 为历史脏数据增加一次性离线修复脚本
- 不相关的 UI 重构

## 旧数据策略

本次只修“新增/后续写入”的统一规则，不做历史数据批量回填。

但展示层和必要的读取逻辑需要兼容旧值：

- 已经是完整 URL 的旧数据应直接可展示；
- 仍为本地相对路径的旧数据继续按 `/static/...` 展示；
- 不尝试在本次自动把旧相对路径转换成 OSS URL。

## 设计方案

### 1. 后端统一落库策略

后端所有图片/视频资源入口统一采用同一判断规则：

1. 调用生成、上传、重绘、重生成服务。
2. 获取服务返回值。
3. 将该返回值视为“最终资源地址候选值”。
4. 若返回值为完整 `http(s)` URL，则数据库直接保存该值。
5. 若返回值不是完整 URL，则优先使用返回值本身；只有当现有链路约定“服务返回值不稳定、但输出路径稳定”时，才允许回退到既有本地相对路径构造逻辑。

### 2. 不再假设本地输出路径一定是最终值

本次修复的核心约束：

- 调用方不得再无条件把 `output_path` 回写数据库。
- 只有在服务返回本地路径、或该链路明确约定需要回退到稳定输出路径时，才允许使用相对路径回写。

这条约束适用于图片与视频链路，防止“生成函数已经返回 OSS URL，但调用方忽略返回值”的问题再次出现。

### 3. 前端 helper 统一兼容两种值

所有资源 URL helper 都统一遵循下面规则：

1. 输入为空 → 返回空。
2. 输入为完整 `http(s)` URL → 原样返回。
3. 输入为项目约定的相对路径（如 `manga_outputs/...`、`video_outputs/...`）→ 转换为对应 `/static/...` 地址。

前端组件不在组件内重复写路径判断逻辑，统一交由 helper 处理。

## 后端实施边界

### 推荐抽象

建议在后端为资源落库增加统一的小型辅助逻辑，职责仅包含：

- 判断返回值是否为完整 URL；
- 是 URL 时直接写入模型字段；
- 不是 URL 时复用既有“相对路径回写”逻辑。

该辅助逻辑应保持轻量，不引入新的复杂资源层。

### 适配方式

对每一类资源入口，检查是否存在以下反模式：

- 服务函数已返回字符串结果；
- 该结果可能是 OSS URL；
- 调用方忽略结果，仅使用预先构造的输出路径写库。

发现此模式的入口全部改为：

- 接收返回值；
- 根据返回值判断最终写库内容。

## 前端实施边界

### 推荐抽象

保留现有 helper 结构，不新增全局资源 SDK。

对现有资源 URL helper 做统一补强：

- 先识别完整 URL；
- 再处理相对路径。

### 组件要求

- 所有展示组件继续只消费 helper 的结果；
- 不在组件内部散落 `startsWith('http')` 等分支；
- 若发现组件直接拼接资源路径，应统一收敛到 helper。

## 风险与兼容性

### 风险 1：二次编辑依赖本地文件

部分资源在“重绘/再次编辑”时，当前逻辑可能假设数据库中保存的是本地相对路径，并直接拼接本地文件路径打开。

例如：

- 封面调整
- 图片重绘
- 某些视频/故事版替换流程

这类链路在统一为“优先保存 OSS URL”后，可能失去直接读取本地文件的能力。

### 应对

对所有二次编辑入口逐一检查：

- 若该入口只支持本地路径，应补远程 URL 下载到临时本地文件的兼容逻辑；
- 或明确要求该类资源在当前流程中必须保留本地副本。

本次设计优先选择“按入口补兼容”，不统一引入大范围临时文件框架。

### 风险 2：前端 helper 命名和路径规则不统一

同类 helper 如果分散在多个文件中，容易修漏。

### 应对

在实施前先列出所有资源 URL helper 与直接拼接点，逐个收口。

## 测试策略

### 后端回归测试

每类代表性资源至少补两类测试：

1. 服务返回 OSS URL 时：
   - 数据库字段保存完整 URL；
   - API 响应返回完整 URL；
   - 不再回退写相对路径。

2. 服务返回本地路径时：
   - 数据库字段仍保存相对路径；
   - API 响应保持当前兼容行为。

### 前端测试

每个资源 URL helper 至少补两类测试：

1. 输入完整 `http(s)` URL → 原样返回。
2. 输入本地相对路径 → 正确转换为 `/static/...`。

### 实际验证

至少手动验证：

- 一条图片生成链路
- 一条视频生成链路
- 一条二次编辑/替换链路（如果该类资源支持）

验证内容包括：

- 数据库字段值
- 接口返回值
- 前端实际回显地址
- OSS 可访问性

## 验收标准

满足以下条件即视为完成：

1. 新生成的图片/视频资源，只要最终落点是 OSS，数据库就保存 OSS URL。
2. 新生成的图片/视频资源，若未使用 OSS，数据库继续保存本地相对路径。
3. 前端展示所有相关资源时，既能正确处理完整 URL，也能正确处理本地相对路径。
4. 不再出现“资源已上传 OSS，但前端仍请求 `/static/...` 本地路径”的同类问题。
5. 现有旧数据在不迁移的情况下仍可展示，不因本次修复大面积失效。

## 推荐实施顺序

1. 盘点所有图片与视频资源入口。
2. 盘点所有前端资源 URL helper 与直接拼接点。
3. 先修后端写库逻辑。
4. 再修前端 URL helper。
5. 最后逐类补测试并做手动验证。
